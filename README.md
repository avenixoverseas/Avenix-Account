# Avenix Overseas — Accounting ERP Professional

Static frontend with Supabase backend for accounting, employee management and payroll.

## Database setup — one clean SQL file

1. Take a full Supabase backup and test restore before changing a live database.
2. Open Supabase SQL Editor and run **only** `supabase/sql/schema.sql`.
3. This consolidated, idempotent setup includes the accounting schema, payroll tables, corrected salary-component defaults, RLS/functions, global activity sequence and atomic payroll posting RPC.
4. Configure `js/config.js` with the correct Supabase project URL and anon/publishable key for the environment you are deploying. The included project URL/key may refer to the existing project; verify ownership and rotate/restrict keys if needed. Never put a service-role key in browser JavaScript.
5. Ensure the designated owner account is correctly provisioned as ADMIN. Review RLS and permissions using a separate STAFF account.

The previous split SQL scripts have been removed from this package. Do not run obsolete SQL copies alongside the consolidated file.

## Salary structure repair

Every salary component now writes `is_statutory` explicitly. Earnings and ordinary deductions use `false`; PF, ESI, TDS and professional tax use `true`. The SQL backfills legacy NULL values, then applies `DEFAULT false NOT NULL`.

## Monthly payroll payment workflow

1. Create/calculate the payroll batch.
2. Open the batch, select its mapped bank account, and choose **Approve & Pay**.
3. Approval immediately invokes the payment RPC. If posting fails after approval, the batch remains APPROVED and can be safely retried with **Pay & Post to Bank**.
4. The `process_payroll_payment` database function runs as one atomic transaction: validates the approved batch, verifies the bank's dedicated ledger mapping, posts balanced salary-expense/bank journal lines, mirrors the bank debit into the operational expense register so the Bank Accounts balance/statement updates, marks payroll lines PAID, creates/updates payslips, marks the batch PAID and records an audit event.
5. Duplicate posting is blocked by row locking and a unique payroll source index.

**Bank integration boundary:** This posts a debit to the ERP's bank ledger and updates the ERP bank balance derived from journal entries. It does not transmit funds through a real bank/payment gateway. Actual NEFT/IMPS/RTGS transfers require a bank API/provider, credentials, beneficiary validation and bank-side confirmation. Never mark a payroll paid based only on an approval.

Each bank account must have its own ledger. The consolidated SQL now backfills missing mappings for existing bank accounts and automatically links newly-created bank accounts. The payment RPC also repairs a legacy missing mapping defensively; it never uses a shared generic bank ledger.

## Global chronological activity numbering

All public business-table inserts, updates and deletes are written to `public.global_activity_log` by database triggers. `event_number` comes from one global sequence shared across tables. Read the activity stream using:

```sql
select event_number, event_at, table_name, action, record_id, actor_id
from public.global_activity_log
order by event_number asc;
```

This is an append-only chronological audit stream, oldest to newest, across modules. Each event is numbered once; event numbers are not reset per menu. The sequence records database mutations, not merely page views or clicks.

## Other operational notes

- Configure Supabase automated backups / PITR separately in the Supabase Dashboard.
- Review PF, ESI, professional tax and TDS settings with your payroll/accounting professional before live use.
- Restrict the Admin User Management Edge Function CORS origin to the production website domain.
- The package cannot execute SQL against your hosted Supabase project; apply the schema to a staging clone first and validate with test employees and a non-production bank ledger.

## Payroll improvements (AVENIX release)

- Employee codes are generated by PostgreSQL using `avenix_employee_code_seq`; the first new code is `AVXT-021` unless a higher AVXT code already exists. Existing employee codes are preserved.
- Existing bank accounts missing a ledger link are assigned their own asset ledger account by the SQL migration. New bank accounts are linked automatically. Payroll payment posting also has a defensive fallback for legacy records.
- Employee entry is grouped into employee, employment, bank/statutory and notes sections.
- Salary structure is sequenced as employee, earnings, deductions and net salary.
- Payslip print layout includes the Avenix logo and a double-line four-sided border.
- Payroll forms and tables use phone-first responsive layouts; wide tables scroll horizontally on small screens.

### Apply the database update

1. Back up the Supabase project before applying database changes.
2. Open Supabase Dashboard → SQL Editor.
3. Run the complete canonical `supabase/sql/schema.sql` file from this release.
4. Verify under Bank Accounts that each active bank account has its own linked ledger account.
5. Add a test employee and confirm its generated code. Do not test payment posting with a real payroll batch or real money.
6. Test payroll with a non-production test batch and bank account before production use.

The SQL is idempotent for the added payroll repair migration, but this is not a substitute for a database backup and staging test. The browser app does not transfer money to a bank; posting creates the ERP journal/expense records only.
